# POD_combat_log_entry: empty story_cycle type used as a row in the
# combat-window log. pod_combat_push_log_effect creates one entry per
# resolved outcome - single-target moves push one entry, AoE phases
# push one per target, and pod_combat_push_system_log_effect pushes
# combat-lifecycle bookends (combat starts / ends, round transitions).
# Stories are OWNED by character:POD_wraith_01 (Charon - same off-map
# anchor as the move catalogue), but REFERENCED from the combat host
# (PC) via the `pod_combat_log` variable list of story refs. The GUI
# iterates the host's list via datamodel and reads each entry's vars
# (move, actor, actor_side, target_char, the three-axis result, the
# rider amounts, aoe_burst_index, system_message, round, log_seq)
# directly from the Charon-owned story scope. Entries are APPENDED
# (chronological, oldest first) with a per-fight log_seq stamp; the GUI
# vbox renders bottomtotop so recent actions show at the top with no
# per-push list rebuild. The cap trim drops the lowest-log_seq entry.
# All entries are end_story-d in pod_combat_cleanup_effect at combat end.
#
# Result captured on each entry follows the three-axis flag model:
# `outcome` (attack / heal / morale_damage / morale_healed / utility),
# `attack_result` (only meaningful when outcome=attack: hp_damage /
# soaked / missed / dodged / stealthed / guard_blocked), and
# `retal_fired` (independent overlay for landed counter-strikes).
# PODCombatLogResultText dispatches on outcome + attack_result;
# PODCombatLogRetalRider reads retal_fired as a side-rider. Full
# contract in COMBAT_REFERENCE.info §4.
#
# Storing the move story scope (rather than a numeric msg_id) lets the
# GUI read move-static properties - emitted capability flags
# (requires_hit_roll, checks_guard, checks_stance,
# checks_spirit_gate), damage_type (the damage class), targeting,
# combat_category — directly from the move's own vars without
# per-move duplication in the log.
POD_combat_log_entry = {
	on_setup = {}
	on_end = {}
	on_owner_death = {}
}


# POD_combat_slot: empty story_cycle type used as a per-slot data
# container during combat. Stories are LAZILY CREATED on Charon —
# pod_combat_set_slot_char_effect creates the story the first time
# a (team, position) cell is populated, so a 1v1 combat carries 2 stories (PC
# + primary opponent), an NvN carries however many slots the mode
# actually filled. All slot stories are end_story-d at combat
# cleanup. Each slot story holds the combatant's per-slot state
# (combat_team, team_position, slot_char, slot_alive, soak, prowess, stance flags,
# tier mods, retaliate, etc.). This is the sole storage for per-slot
# combat state.
#
# Stored on character:POD_wraith_01 (Charon, same off-map anchor used
# by the move catalogue, log entries, and sc_context). The combat
# host references the slot stories two ways:
#   1. pod_combat_active_slots — variable list of every filled slot
#      story, in insertion order (player 0-4, then enemy 0-4). Every dispatch loop
#      iterates this list (initiative, find_next_actor, AoE
#      damage/heal/buff/debuff, victory check, GUI datamodel, etc.).
#   2. pod_combat_player_slot_{0..4} / pod_combat_enemy_slot_{0..4} —
#      up to ten named pointer vars, one per cell the duel builder
#      actually filled. Used for parametric direct access
#      (`var:pod_combat_$TEAM$_slot_$POS$` resolves to the slot story
#      at compile time when $TEAM$ / $POS$ are parametric literals).
#      Unfilled cells have no pointer var.
# end_story-d in pod_combat_clear_slot_stories_effect, which is called
# from pod_combat_group_cleanup_effect at combat end. All slot vars go
# with the story, so no per-field cleanup pass is needed.
POD_combat_slot = {}

# two lines.
